# BUAA HEP Lab 网站设计与开发路线图

> 用途：长期开发计划与跨会话交接文档。每次继续开发前，先核对本文件的当前状态和下一步任务。
> 仓库：[`lm846802297-bit/buaa-hep-lab`](https://github.com/lm846802297-bit/buaa-hep-lab)
>
> **总原则：先完成用户能看到、能使用的功能；工程与安全工作按实际风险推进，不作为普通 UI 开发的统一前置门槛。**

## 1. 项目目标

建设一个具有辨识度的高能物理课题组官网，并逐步扩展为内部科研协作空间。公开页面应便于了解课题组、研究方向、成员、论文和学术活动；内部功能逐步支持组会、通知、任务、文件与研究记录。

### 当前不应阻塞公开网站开发的事项

- GitHub Actions 因账户付款或 spending limit 无法启动。
- Preview 环境的 D1/R2/密钥配置尚未完成。
- 暂未启用的登录、邮件或文件上传功能。
- 与普通 UI 修改无关的完整后端测试。

但必须如实记录未验证项，不得把未运行的检查标记为通过；Preview 隔离未确认前，不执行可能触及生产数据的测试。

## 2. 设计方向

### 2.1 主视觉：Scientific Atelier（学术绘图室）

以用户认可的粒子物理课题组首页概念图为首要视觉基准。

- 暖白/浅灰纸张质感，细密工程网格、测量标记和技术绘图辅助线。
- 手绘机械齿轮、粒子轨迹、物理草图与克制的公式注释。
- 优雅的大号衬线标题，正文清晰易读。
- 深蓝作为主强调色，少量琥珀色作为视觉焦点。
- 首页可有丰富演出，但研究专题、论文库和学术活动页优先可读、可检索。
- 手机端保留同一视觉语言，同时减少背景细节和高成本动效。

### 2.2 第二主题：Steins;Gate-inspired 科研终端

作为独立可切换主题，不取代主视觉。

- 冷蓝黑、复古电子设备、科研终端、扫描效果、细线图形。
- 支持悬停、点击、面板切换、短暂扫描线、粒子/轨迹转场。
- 主题切换时**不出现“世界线变动”等文字**，只保留视觉演出。
- 不让霓虹效果影响正文、公式和论文元数据的可读性。
- 支持键盘焦点，并尊重系统减少动态效果偏好。

### 2.3 设计系统逐步统一

逐步统一颜色、字体、间距、边框、圆角、阴影、内容宽度、导航、页脚、卡片、按钮、标签、目录、搜索框、空状态、错误状态、动效时长和响应式断点。优先复用已有实现；不要为了抽象化而一次性重写所有页面。

## 3. 六个功能模块

### 模块 1：公开官网（当前优先）

范围：
- 首页、课题组简介、研究方向总览。
- 团队成员、公开成果、联系方式与外部链接。
- 全局导航、页脚、搜索入口。
- 移动端适配、主主题和终端主题切换。
- 悬停、点击、页面转场等效果。

验收：
- 核心入口明确，链接有效。
- 首页、研究方向、团队页风格统一。
- 手机端无明显横向溢出、按钮遮挡或无法操作的菜单。
- 正文对比度和键盘焦点可用。
- 构建成功，公开页面不依赖登录、D1 或 R2 才能显示。

### 模块 2：研究专题与论文库

范围：
- 研究专题索引与详情、论文和预印本、引用信息。
- Markdown、公式、图表、附件展示。
- 专题与论文、研究记录之间的关联。
- 来源链接、更新时间与必要的 commit 追溯。

验收：
- 专题具有稳定 URL 和清晰目录。
- 论文元数据一致，外链正确。
- 公式、代码块、图片和移动端排版正常。
- 缺失的单条资料不会导致整个页面崩溃。
- 私有研究材料不会意外进入公开页面。

### 模块 3：组会与学术活动

范围：
- 组会日历、活动列表、报告人、标题、摘要和地点/会议链接。
- 历史报告归档、幻灯片和相关资料链接。
- 后续可增加提醒和日程导出。

验收：
- 日期、时区、过去/未来活动状态正确。
- 空列表、取消活动和缺失字段有合理展示。
- 历史活动可查询；涉及 API 时测试权限和错误状态。

### 模块 4：组内协作 Hub（后续）

范围：
- 登录、账户和角色权限。
- 通知、任务、讨论、内部日程与提醒。
- 文件共享、个人设置和研究资料入口。
- 研究记录索引和来源追溯。

验收：
- 未登录用户无法访问受保护数据。
- 角色读写权限符合预期。
- 会话过期、登录失败和无权限操作有清晰反馈。
- 开发测试数据与生产数据隔离。

### 模块 5：邮件与通知（按需启用）

范围：
- 站内通知、用户偏好、邮件流程、状态记录。
- HTML 邮件安全展示和错误处理。

验收：
- 通知权限正确。
- 邮件 HTML 不执行非预期脚本。
- 真实邮件凭据不进入仓库或公开日志。
- 恶意 HTML 人工验收只在确认隔离的环境执行。

### 模块 6：基础设施与工程维护（持续、但不阻塞普通 UI）

范围：
- GitHub 分支与 PR、本地测试、CI、Pages 部署。
- D1/R2 绑定、依赖安全、备份、故障排查和部署证据。

验收：
- 变更能定位到准确 commit。
- 区分本地验证、CI、预览部署和生产部署。
- 环境绑定可核对，失败能定位到具体阶段。
- 不通过提高预算、跳过检查或伪造状态来“修复”失败。

## 4. 开发阶段与顺序

### 阶段 A：完善公开官网（现在开始）

1. 盘点当前 `main` 和开放 PR 中已经存在的页面与改动，避免重复开发。
2. 统一全局导航、页脚、内容宽度和响应式规则。
3. 完善首页信息层级与 Scientific Atelier 主视觉。
4. 完善研究方向、团队和公开成果页面。
5. 完成终端主题切换、悬停、点击和页面转场。
6. 检查手机端、键盘操作与减少动态效果。
7. 对具体修改执行针对性前端测试、构建和必要截图验收。

完成定义：公开核心页面完整、视觉统一、主要链接有效、手机端可用、构建通过。

### 阶段 B：研究专题与论文库

1. 盘点现有专题与论文页面。
2. 统一专题和论文的数据结构、目录与来源链接。
3. 完善搜索、过滤、公式、图表和附件展示。
4. 明确公开内容与私有研究材料的边界。

完成定义：研究资料易于浏览和检索，来源清楚，页面不依赖内部认证服务。

### 阶段 C：组会与学术活动

1. 先做活动只读展示。
2. 再实现数据编辑和权限。
3. 增加历史归档、提醒和资料关联。
4. 测试日期、时区、取消活动和权限。

完成定义：活动信息准确、日历可用、权限边界有测试。

### 阶段 D：内部 Hub

1. 明确角色、权限和最小用户流程。
2. 完成登录与会话管理。
3. 完成通知、任务和个人设置。
4. 再增加文件共享和复杂协作。
5. 在需要运行认证 API 前，配置隔离的开发/预览资源。
6. 对认证、权限和写入路径执行专项测试。

完成定义：核心协作流程可用，未授权访问被拒绝，测试不触及生产数据。

### 阶段 E：邮件与通知

1. 优先完成站内通知。
2. 确认是否真的需要邮件收发。
3. 配置专用测试凭据和隔离环境。
4. 实现安全 HTML 展示和错误处理。
5. 隔离环境人工验收完成后，再决定是否启用生产邮件能力。

### 阶段 F：工程流程优化

1. 处理 GitHub Actions 计费/额度阻塞。
2. 恢复准确 SHA 的 CI。
3. 减少重复依赖安装和浏览器下载。
4. 评估缓存和构建产物复用。
5. 在真正需要后端功能时，再完成 Preview 的 D1/R2/密钥隔离。
6. 只在准备发布对应功能时，完成该功能所需的安全验收。

## 5. 任务优先级

### P0：现在做
- 首页、导航、团队、研究方向的视觉和交互。
- 移动端布局与明显 UI 缺陷。
- 公开论文与专题内容展示。
- 主题切换和动效。
- 不依赖后端的页面优化。

### P1：主线完成后或并行
- 研究专题和论文库。
- 组会和活动页面。
- 搜索、目录、索引和内容组织。
- 前端组件复用与性能优化。

### P2：对应功能需要时再做
- 登录、权限和会话管理。
- 内部 Hub 写入流程。
- D1/R2 资源配置。
- 邮件发送/接收与恶意 HTML 验收。
- 生产数据迁移和发布审计。

### 不要做
- 不为普通颜色、排版修改运行全部后端测试。
- 不把 CI 不可用等同于网站不能开发。
- 不把未运行的检查标记为通过。
- 不为让检查变绿而删除测试、放宽约束或提高预算阈值。
- 不在隔离未确认的 Preview 上执行可能访问生产数据的测试。
- 不未经明确授权修改生产资源、合并高风险 PR 或发布生产版本。
- 不重复重做已经完成且经过核实的工作。

## 6. 按风险选择验证强度

| 风险 | 常见改动 | 最小验证 | 通常不需要 |
|---|---|---|---|
| 低 | CSS、排版、卡片、静态文案、普通动效 | 相关前端测试、构建、必要截图/手工检查 | 完整后端套件、数据库迁移测试 |
| 中 | 路由、数据映射、搜索、活动逻辑、API | 针对性测试、相关回归、构建 | 与改动无关的完整审计 |
| 高 | 登录、权限、密码、密钥、邮件 HTML、数据库迁移、生产绑定 | 安全回归、权限验证、环境隔离证据；可用时跑完整测试 | 用普通 UI 测试替代安全验收 |

CI 不可用时：
1. 继续运行本地能够执行的验证。
2. 记录准确 SHA、命令、退出码和失败信息。
3. 标记“本地通过”“CI 未运行”“环境阻塞”或“尚未验证”。
4. 只有高风险或发布事项因缺少必要证据而暂缓；普通 UI 任务继续推进。

## 7. PR 与部署工作流

### 普通 UI 修改
1. 从当前合适的分支开始。
2. 只修改任务相关文件。
3. 执行相关前端测试和构建。
4. 检查 diff、截图和移动端效果。
5. 提交到对应分支/PR。
6. 独立判断是否合并和是否生产发布。

### 中高风险修改
1. 明确需求、数据边界和影响范围。
2. 先定义针对性测试。
3. 实施最小改动。
4. 检查失败路径和权限边界。
5. 获取本地/CI 证据。
6. 必要验收未完成时，不进入生产发布。

规则：
- 以准确的当前 `main` 和 PR HEAD 为准。
- 移植修复前先比较差异，避免共享文件冲突。
- “可合并”不等于“应该合并”。
- 预览部署成功不等于数据隔离成功。
- 本地测试通过不等于 CI 通过。
- 生产发布需要独立确认。
