## 1. 结论

**项目可以改造成适合并行开发的模式，无需推倒重写。** 目前已有 Vue 组件/视图、主题 composable、按业务域拆分的 Pages Functions 路由、FastAPI 路由以及较丰富的单元和浏览器测试。主要瓶颈不是“完全没有模块化”，而是：

1. `main` 的保护状态没有得到可靠确认；
2. 历史协作/部署文档仍包含直接部署、直接推送 `main` 和过期资源名；
3. 多个未合并 PR 同时修改全局 CSS、主题系统和同一浏览器测试文件；
4. 部分 PR 分支相对当前 `main` 已过时，最新 HEAD 的 CI 状态不一致；
5. 全局 CSS、主题状态和大页面是高冲突热点；
6. Cloudflare Pages Functions 与自建 FastAPI 是两套后端实现，数据库 schema 还存在运行时补列逻辑，接口与迁移需要更明确的契约；
7. 全量 FastAPI 测试已纳入当前 main 的发布验证；剩余的主要风险是开放 PR 的最新 HEAD 仍需逐条验证，以及主题/专题 PR 存在共享文件交集。

因此应先修复协作规则和合并门槛，再逐步拆分高耦合模块；不建议一次性重构全站。

### 2.3 模块化基础与共享热点

已看到以下正向结构：

- 页面：`frontend/src/views/`
- 通用组件：`frontend/src/components/`
- 复用逻辑：`frontend/src/composables/`
- Cloudflare API：`frontend/functions/api/routes/` 按业务域拆分
- 自建后端：`backend/routers/`、`backend/services/`
- 前端 API 客户端：`frontend/src/api/client.js`

但以下文件具有明显的跨功能影响范围：

| 热点 | 观察 | 并行开发风险 |
|---|---|---|
| `frontend/src/index.css` | 约 2,464 行、114 KB，包含基础元素、工作台布局、侧栏、卡片、响应式和多主题规则 | 多个 UI PR 容易覆盖、叠加或改变其他页面样式 |
| `frontend/src/composables/useThemeStyle.js` | 约 30 KB，集中管理主题注册、持久化、迁移、背景/玻璃选项和 DOM 状态 | 主题偏好、首次绘制和跨页面恢复可能互相影响 |
| `frontend/src/App.vue`、`frontend/index.html` | 影响全局壳层、主题首次绘制和公共/工作台切换 | 小改动也可能影响所有路由 |
| `frontend/tests/audit-browser-smoke.mjs` | 共用浏览器验收脚本，被多项 UI PR 修改 | 测试夹具或定位器冲突会影响不同功能的验收 |
| `frontend/functions/api/[[route]].ts`、`frontend/functions/api/types.ts` | 全局 API 挂载与运行时类型/绑定 | 新路由、公共中间件和环境变量变更需要协调 |
| `scripts/schema_d1.sql`、D1 绑定和后端模型 | 多个功能共享持久化数据结构 | 并行 schema 变更可能不兼容或遗漏迁移 |

这些是应建立“共享热点协调规则”的文件，并不意味着应马上把所有文件重写。

### 2.6 后端与 schema 风险

Cloudflare 托管端使用 Pages Functions + Hono + D1；自建模式使用 FastAPI + SQLite。两者是两条真实的实现路径，不能把一个路径的测试通过视为另一个路径行为一致。

此外，当前 `frontend/functions/api/routes/auth.ts` 与 `routes/files.ts` 中可见请求运行期间补列/更新 schema 的逻辑。这种方式有兼容旧数据库的价值，但当多个功能 PR 并行修改表结构时，会让 schema 的权威来源、执行顺序、失败恢复和重复执行更难审计。应逐步改成可追踪的迁移记录，并建立双后端 API 契约测试。
