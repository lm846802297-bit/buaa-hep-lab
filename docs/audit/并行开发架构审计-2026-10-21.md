- 限制：本报告基于 GitHub 当前代码、PR 元数据、Actions 运行记录和仓库文档；未直接访问 Cloudflare Dashboard 的设置，也未独立执行本地全量测试。

## 1. 结论

**项目可以改造成适合并行开发的模式，无需推倒重写。** 目前已有 Vue 组件/视图、主题 composable、按业务域拆分的 Pages Functions 路由、FastAPI 路由以及较丰富的单元和浏览器测试。主要瓶颈不是“完全没有模块化”，而是：

1. `main` 的保护状态没有得到可靠确认；
2. 历史协作/部署文档仍包含直接部署、直接推送 `main` 和过期资源名；
3. 多个未合并 PR 同时修改全局 CSS、主题系统和同一浏览器测试文件；
4. 部分 PR 分支相对当前 `main` 已过时，最新 HEAD 的 CI 状态不一致；
5. 全局 CSS、主题状态和大页面是高冲突热点；
6. Cloudflare Pages Functions 与自建 FastAPI 是两套后端实现，数据库 schema 还存在运行时补列逻辑，接口与迁移需要更明确的契约；
7. CI 对前端覆盖较完整，但 Python 后端仅运行部分测试。

因此应先修复协作规则和合并门槛，再逐步拆分高耦合模块；不建议一次性重构全站。

## 2. 已验证的现状

- 在 PR 上执行验证；
- 在 `main` push 上先运行 `validate`，通过后才运行 `deploy`；
- 发布后执行线上健康和授权检查。

审计基准提交 `5d80776a78275fbe2fc4b3a7d204070d7965e2af` 的 Actions 运行 [#39594542258](https://github.com/lm846802297-bit/buaa-hep-lab/actions/runs/39594542258) 中，`validate` 与 `deploy` 均成功，部署后的健康/授权检查也成功。这证明该提交的发布闭环通过，不代表其他 PR 的最新 HEAD 也通过。

### 2.2 主分支保护

GitHub 的 `main` 分支元数据返回 `protected: false`。本次连接无法读取仓库 Rulesets 的完整设置，因此**传统 branch protection 未显示启用，而 Ruleset 是否另外保护主分支仍待人工验证**。当前不应假定 GitHub 已经强制所有变更走 PR。

### 2.3 模块化基础与共享热点

已看到以下正向结构：

- 页面：`frontend/src/views/`
- 通用组件：`frontend/src/components/`
- 复用逻辑：`frontend/src/composables/`
- Cloudflare API：`frontend/functions/api/routes/` 按业务域拆分
- 自建后端：`backend/routers/`、`backend/services/`
- 前端 API 客户端：`frontend/src/api/client.js`

但以下文件具有明显的跨功能影响范围：

| 热点 | 观察 | 并行开发风险 |
|---|---|---|
| `frontend/src/index.css` | 约 2,464 行、114 KB，包含基础元素、工作台布局、侧栏、卡片、响应式和多主题规则 | 多个 UI PR 容易覆盖、叠加或改变其他页面样式 |
| `frontend/src/composables/useThemeStyle.js` | 约 30 KB，集中管理主题注册、持久化、迁移、背景/玻璃选项和 DOM 状态 | 主题偏好、首次绘制和跨页面恢复可能互相影响 |
| `frontend/src/App.vue`、`frontend/index.html` | 影响全局壳层、主题首次绘制和公共/工作台切换 | 小改动也可能影响所有路由 |
| `frontend/tests/audit-browser-smoke.mjs` | 共用浏览器验收脚本，被多项 UI PR 修改 | 测试夹具或定位器冲突会影响不同功能的验收 |
| `frontend/functions/api/[[route]].ts`、`frontend/functions/api/types.ts` | 全局 API 挂载与运行时类型/绑定 | 新路由、公共中间件和环境变量变更需要协调 |
| `scripts/schema_d1.sql`、D1 绑定和后端模型 | 多个功能共享持久化数据结构 | 并行 schema 变更可能不兼容或遗漏迁移 |

这些是应建立“共享热点协调规则”的文件，并不意味着应马上把所有文件重写。

### 2.5 测试门槛

当前 CI 包含前端测试、生产构建、bundle 预算、Chromium 浏览器 smoke 和隔离 Pages 运行时安全检查，这是有价值的基础。

但 Python 后端测试步骤目前只执行：

- `backend/test_security_regressions.py`
- `backend/test_optional_registration.py`
- `backend/test_system_setup.py`

而仓库中还存在其他 FastAPI 路由、服务、权限、组会、文献和数据工作流测试。因此，改动 `backend/` 时，全量 Python 测试并不是当前 CI 的强制门槛，需要在后续 CI 改造中补齐或明确分层执行策略。

### 2.6 后端与 schema 风险

Cloudflare 托管端使用 Pages Functions + Hono + D1；自建模式使用 FastAPI + SQLite。两者是两条真实的实现路径，不能把一个路径的测试通过视为另一个路径行为一致。

此外，当前 `frontend/functions/api/routes/auth.ts` 与 `routes/files.ts` 中可见请求运行期间补列/更新 schema 的逻辑。这种方式有兼容旧数据库的价值，但当多个功能 PR 并行修改表结构时，会让 schema 的权威来源、执行顺序、失败恢复和重复执行更难审计。应逐步改成可追踪的迁移记录，并建立双后端 API 契约测试。

## 3. 已确认的文档治理问题

`docs/CODEX_COLLABORATOR_WORKFLOW.md` 仍包含直接运行生产 `pages:deploy`、随后 `git push origin main` 的步骤，并使用 `labhub` / `labhub-db` 等历史资源名；当前 `frontend/wrangler.json` 中使用的 Pages 项目名和 D1 数据库名为 `buaa-hep-hub` 与 `buaa-hep-hub-db`，当前生产发布由 GitHub Actions 管理。

`docs/CLOUDFLARE_DEPLOYMENT.md` 也包含旧资源名及与当前 R2 未绑定状态不一致的部署说明。

这类文档冲突会让不同 AI Agent 按不同操作规程工作，是并行开发的实际风险。本次治理 PR 暂不改写这两份文件，因为打开的 PR #3 正在修改同一批发布/协作文档；避免新开一个相互覆盖的 PR。应在 PR #3 的 SEC-04 工作完成或明确拆分后，统一清理旧文档。

## 4. 推荐整改顺序

### P0：建立可执行的协作边界

1. 在 GitHub Settings 中确认并保护 `main`：PR 必需、当前 HEAD 的 CI 必需、禁止 force-push/删除、解决讨论；审批要求应与实际维护人数匹配。
2. 将 PR-first 规范写入 `AGENTS.md` 和统一协作指南；明确禁止默认直接推送 `main`、直接生产部署和未经授权的远程 D1 写入。
3. 新增 PR 模板，要求提交者说明变更范围、共享热点、API/schema 影响、测试 SHA、风险和回滚方式。

### P1：收敛当前 PR 并行冲突

1. 先确定 PR #7、#14、#15 哪些工作仍然需要；避免同一主题兼容性修复被多个分支重复维护。
2. 每次只选择一个主题系统基础 PR 集成；其余相关 PR 以最新 `main` 为基础更新，再验证。
3. PR #3 的 SEC-04 审计应单独完成，不要因本次并行开发治理而绕过它的验证要求。
4. 在 PR #3 对工作流文件的变更解决后，再单独调整 CI 并发策略：取消同一 PR 过时的验证运行，但不取消 `main` 的生产发布运行。

### P2：补齐验证闭环

1. 评估并将全量 FastAPI 测试加入 CI，或至少建立按路径触发的后端测试任务。
2. 为 Pages Functions 与 FastAPI 的共用 API 建立契约测试。
3. 为 D1/SQLite schema 建立可重复的版本化迁移和兼容性检查。
4. 对主题、导航、物理专题内容和后端业务域建立明确的测试矩阵与责任边界。

### P3：逐步拆分高耦合实现

在行为测试稳定后，分阶段拆分全局 CSS 的基础变量、公共官网、工作台布局、主题规则和组件样式；再将主题注册、持久化、首次绘制和动效生命周期分离。对 `StyleView.vue`、`MailboxView.vue`、`SeminarView.vue` 等大型视图也应按业务职责渐进提取组件，而不是一次性重写。
