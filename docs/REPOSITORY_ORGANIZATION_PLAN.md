# 仓库整理计划

> 状态：提案。本文用于安排低风险、可分阶段的整理工作，不授权删除研究资料、改变应用行为、合并功能 PR 或触发生产部署。
>
> 基准：初始整理分支建立时 `main` 的 HEAD 为 `abc6cc2b5c1b12697af7346a1e565db72a6b4bae`；阶段 1 后续合并提交为 `a648585f4f1e6e64cdf896dcbd5a558a351cde60`。执行后续阶段前必须重新读取最新 `main` 与开放 PR。
>
> 当前进度（2026-10-26）：阶段 1 已由 PR #63 合并；阶段 2 的 README 精简通过 PR #65 与 PR #62 协调推进；阶段 3 的测试/脚本命令映射见 `docs/TESTING_AND_VALIDATION.md`，需随实际脚本变化维护。

## 1. 目标

让仓库更容易理解、导航、开发和交接，同时保留已有功能与研究证据。整理的成功标准不是文件越少越好，而是：

- 新贡献者能快速知道从哪里开始；
- 规范、路线图、审计记录和历史研究材料职责清楚；
- 普通 UI 任务能快速找到对应测试与验证命令；
- 不因移动文件、重写配置或合并分支破坏当前功能；
- 所有“通过”结论都能对应到准确提交与实际证据。

## 2. 当前结构概览

当前 `main` 包含约 534 个跟踪路径，主要分区如下：

| 路径 | 当前职责 | 整理判断 |
|---|---|---|
| `frontend/` | Vue/Vite 前端、Cloudflare Pages Functions、前端测试与构建脚本 | 先保留现有结构；按职责审查，不进行大规模组件搬迁 |
| `backend/` | FastAPI/SQLite 后端、路由、服务、测试和迁移 | 结构基本按职责分组；测试清理与服务边界另行专项处理 |
| `deploy/`、根目录启动脚本 | Docker 与本地/服务器启动入口 | 统一文档入口，但暂不重写部署行为 |
| `scripts/`、`frontend/scripts/` | 仓库级检查和前端构建/内容检查脚本 | 明确每个脚本的唯一职责、调用方与适用场景 |
| `.github/workflows/` | CI、部署和专项检查工作流 | 不在文档整理 PR 中修改；后续单独核查触发条件与发布边界 |
| `docs/architecture/` | 模块、存储等架构契约 | 作为架构设计与边界文档的主要位置 |
| `docs/design/`、`docs/planning/` | UI 设计、外部研究和产品规划 | 需要明确哪些是当前规范、哪些是历史研究/候选方案 |
| `docs/audit/` | 审计报告、测试基线、内容核查和证据快照 | 保留证据；标记时间和适用 SHA，不能把旧报告直接当作当前状态 |
| `docs/cloud-migration/` | 云迁移专项材料、脚本与模板 | 保持独立专题，不与常规网站文档混在一起 |
| 根目录 `README.md` | 项目介绍、部署说明、功能清单及较长的中英文历史说明 | 后续需要分阶段精简；当前有开放 PR #62 修改 README，暂不并行改写 |
| 根目录 `design.md` 与 `docs/design/` | UI 长期实现规则与详细改版方案 | 职责不同，不应直接合并；通过索引说明关系 |

## 3. 当前已识别的整理问题

### 3.1 文档入口不足

根目录 README 内容较长，同时承担项目介绍、快速上手、功能说明、部署说明和历史来源介绍等职责。虽然已有 `docs/DEVELOPMENT_ROADMAP.md`，但还缺少统一的 `docs/` 导航入口。本分支先补齐索引，暂不改写 README，以避免与 PR #62 的改动冲突。

### 3.2 文档角色容易混淆

仓库中同时存在：

- `AGENTS.md`：开发代理/贡献流程的执行规则；
- `design.md`：前端 UI 的长期实现规范；
- `docs/DEVELOPMENT_ROADMAP.md`：项目阶段与开发优先级；
- `docs/design/`：详细的页面改版设计方案；
- `docs/planning/`：外部对标研究和内容规划；
- `docs/audit/`：特定时间、提交或环境的审计与证据。

这些文件并非天然重复。整理时应明确职责和交叉链接，不应把设计方案、长期规范和历史审计强行合并为一个超大文档。

### 3.3 时间敏感的证据需要防止误用

审计报告、测试基线、部署结论可能只适用于某个 commit 或环境。后续可为相关报告统一补充元数据：检查日期、目标 SHA、执行命令、结果、限制和复核状态。历史证据应保留，不能为了“清爽”而删除。

### 3.4 测试与脚本数量较多

前端组件测试、前端集成/浏览器测试、后端测试、Cloudflare 类型检查、模块边界检查和部署工作流分散在不同目录。后续应建立测试入口表，按改动风险列出最小验证命令，而不是把所有测试强行移动到单一目录。

### 3.5 PR 之间有共享文件交集

当前开放 PR 包括安全修复、README/部署文档、主题设计、品牌页面、模块边界和依赖审计等任务。部分 PR 会修改同一测试、样式、README 或前端入口。整理工作必须独立成支线，避免修改这些共享热点；先检查 PR 文件清单和 base/head，再决定集成顺序。

## 4. 分阶段执行方案

### 阶段 0：建立基线（只读）

- 记录最新 `main` SHA、根目录树、主要工作流与包脚本。
- 列出开放 PR 的标题、base/head、变更文件和共享文件交集。
- 记录文档的路径、职责、日期和相互引用。
- 标记明显过时或可能重复的材料，但不立即删除。

**完成标准：** 有结构清单和风险清单；没有源代码或部署变更。

### 阶段 1：建立文档导航（已完成，PR #63）

- 新增 `docs/README.md` 作为文档总入口。
- 新增本计划，记录后续整理顺序和禁止事项。
- 为各类文档说明维护职责与状态判读规则。
- 不移动/删除现有文件，不改应用代码、工作流或 Cloudflare 配置。

**完成记录：** PR #63 已合并，新增 `docs/README.md` 与 `docs/REPOSITORY_ORGANIZATION_PLAN.md`；未移动或删除既有文件。

### 阶段 2：精简根 README（等待共享文件窗口）

- 等 PR #62 对 README 的改动结束后，重新读取最新 README。
- 将 README 的职责收敛为：项目定位、主要功能、开发快速开始、部署方式摘要和关键文档入口。
- 详细部署步骤链接到 `docs/CLOUDFLARE_DEPLOYMENT.md` 与自建部署指南（若该文件已合并）。
- 将过长的功能清单或历史来源内容移动到专门文档前，先检查所有内外部引用。
- 保留许可证、来源和必要归属信息；不删除仍有用途的说明。

**完成标准：** README 更短但能完成快速上手；链接检查通过；所有迁移内容有明确新位置；不与开放 PR 冲突。

### 阶段 3：测试与脚本入口清晰化

- 在文档中列出前端单元测试、后端回归、构建、bundle、浏览器烟测、Cloudflare 类型/边界检查的用途。
- 明确哪些命令适用于纯 UI、API、认证、数据库迁移和部署改动。
- 检查根 `package.json` 与 `frontend/package.json` 的脚本是否存在重复、命名歧义或未引用脚本。
- 不删除脚本、不改 CI 触发条件；先形成映射和证据，再另开实现 PR。

**完成标准：** 每类任务有清楚的验证入口；不依赖 CI 是否可用来判断文档是否准确。

### 阶段 4：前端结构与模块边界审查

- 对照 `docs/architecture/MODULE_BOUNDARIES_AND_OWNERSHIP.md` 与现有检查脚本。
- 检查 `frontend/src/components`、`views`、`composables`、`services`、`utils`、`content` 的职责边界。
- 识别过大的组件、跨主题样式泄漏和循环/隐式依赖。
- 仅对有明确收益的代码进行小批量重构；每批单独测试和审查。
- 不按文件数量或命名喜好批量移动 Vue 组件。

**完成标准：** 每个重构都有具体问题、影响范围、测试证据和可回滚的差异。

### 阶段 5：历史文档治理（最后处理）

- 对 `docs/audit/` 中的报告标注历史/当前、适用 SHA 与是否已复核。
- 将真正过时的状态移入归档子目录前，先搜索全仓引用和外部链接。
- JSON 基准、截图、研究候选和安全证据默认保留。
- 对重复文档先决定唯一维护源，再把其他文档改为链接或标记为历史；未经确认不删除。
- 文件移动/重命名需同步更新 Markdown 链接、脚本、工作流和 PR 模板。

**完成标准：** 文档状态清楚，证据可追溯，旧记录仍可访问。

## 5. 各阶段变更范围与排除项

### 阶段 1（已完成）

PR #63 只新增了 `docs/README.md` 与本计划，并已合并到 `main`。没有移动/删除文件，也没有修改应用代码、工作流或部署配置。

### 测试与脚本入口矩阵（独立文档 PR）

`docs/TESTING_AND_VALIDATION.md` 记录当前 `main` 中实际存在的测试入口和风险分级建议。相关 PR 只应更新文档索引、本文进度与测试矩阵，不修改应用行为。

### 后续阶段的通用边界

- 不在文档整理 PR 中顺带修改 `frontend/` 或 `backend/` 的应用行为。
- 不移动或删除现有文件，除非后续专项任务已检查全仓引用、脚本和外部链接。
- 不修改 `package.json`、锁文件、工作流或部署脚本来追求表面整洁；此类修改应有独立理由与验证。
- 不修改 Cloudflare、D1、R2、Secrets 或生产环境。
- 不合并、关闭或改写无关功能 PR。
- 不声称 CI 或本地代码测试通过，除非对应检查在准确 SHA 上实际运行并成功。
- 不把尚未合并的 PR #57 模块边界/类型检查当成当前 `main` 已有能力。

## 6. PR 与验证策略

- 从准确的当前 `main` 建立独立分支。
- 创建 PR，说明这是 add-only 的文档组织变更。
- 检查新增 Markdown 的相对链接是否指向当前分支中存在的文件。
- 查看 diff，确认没有应用代码、工作流或配置变更。
- 纯文档改动不运行完整前后端测试；CI 仍按账户额度状态单独记录。
- PR 合并前重新检查是否与最新 `main`、PR #62 或其他文档变更冲突。

1. **阶段 1 已完成**：PR #63 已合并，文档总入口与整理计划已进入 `main`。
