# GPT 优先的仓库开发工作流

## 目标与适用范围

本项目以 **GPT / ChatGPT 为主要开发入口**，DSH 与 WorkBuddy 为辅助开发工具。当前不为 Claude Code、Cursor、Windsurf、Gemini CLI 或 GitHub Copilot 维护独立配置；只有未来确有使用需求时再增加适配。

所有工具共用仓库中的规范，不建立相互矛盾的多套流程：

1. 根目录 `AGENTS.md`：最高层项目规则。
2. `docs/PARALLEL_DEVELOPMENT_WORKFLOW.md`：分支、PR、并行开发和验证规范。
3. `.agents/skills/vibe-coding-lab-orbit/SKILL.md`：具体实施与安全操作指南。
4. 相关模块的架构文档、当前源代码、配置和测试。

## GPT / ChatGPT 开始修改前的强制步骤

GPT 通过 GitHub 连接器直接读取或修改仓库时，未必拥有本地终端或 GitHub CLI。因此，**检查目标必须强制，执行方式不强制**：有本地 checkout 和有效 `gh` CLI 时运行预检脚本；否则用已授权的 GitHub 连接器完成等价的只读检查，不得因为没有 CLI 就跳过。

### 1. 明确任务边界

- 用一句话写清目标、验收标准和不在本次范围内的内容。
- 列出准备新增、修改或删除的所有仓库相对路径。
- 先读上面的统一规则，并检查这些路径的当前内容与调用关系。

### 2. 获取实时 GitHub 证据

在任何文件写入之前：

1. 读取 GitHub 上最新 `main` SHA。
2. 列出所有以 `main` 为目标分支的开放 PR（包括 Draft）。
3. 获取相关 PR 的最新 head SHA 和 changed-files 列表；对计划修改的路径，不能只检查当前会话创建的 PR。
4. 将计划路径与这些列表求交集，并记录 main SHA、相关 PR 编号 / head SHA、交集结果。
5. 确认任务分支基于最新 `main`。若分支落后、远端状态无法确认或发现路径交集，先停止写入，更新基线或协调任务所有权。

GPT 使用 GitHub 连接器时，按以上步骤读取 GitHub API/连接器结果即可，不要声称已经在远程环境执行了本地脚本。可在本地终端运行预检工具的环境使用：

```bash
node scripts/agent-preflight.mjs --paths <path1> <path2> ...
```

脚本只刷新本地 `origin/main` 跟踪引用并读取 GitHub 信息；它不修改源代码或远程分支。预检覆盖选项只能在用户明确授权后使用。

### 3. 功能开发与 PR 生命周期

- **一个明确、可验收的功能目标对应一个 PR。** PR 可以涉及多个文件，但必须围绕同一验收目标；紧密耦合的前后端、测试和文档可以放在一起，并在描述中说明依赖关系。不要把无关功能塞进同一个 PR。
- 在任务分支和范围确定后，**尽早创建 Draft PR**，让其他会话看到正在开发的目标、负责人、文件范围和依赖。PR 未完成时保持 Draft，不代表失败，也不要求提前合并。
- 每个 PR 完成后独立审查、独立验证。满足审查与 CI 门槛后就可以合并，**不等待无关功能一起完成**；不要为了减少操作而积累大量已完成但未处理的 PR。
- 存在真实依赖时按顺序合并：先合并基础接口、共享组件或 schema，再更新依赖它的分支。每次合并后，都要检查其他开放 PR 是否需要同步最新主分支、解决冲突或重新运行受影响的测试。
- GPT / ChatGPT 是主要开发入口，负责重点代码审查、跨 PR 依赖协调、合并顺序判断和最终集成验收。DSH 与 WorkBuddy 等其他会话可以承担各自功能的实现和初步测试，但其测试结论不能替代 GPT 对关键差异和跨功能风险的复核。
- GPT 通过 GitHub 连接器直接提交文件时，需逐项核对写入后的实际 diff 和最新 HEAD；不要仅凭工具返回“成功”就认定代码正确。
- DSH 与 WorkBuddy 必须遵循同一规则。如果工具支持读取 AGENTS.md，应先加载它；具体工具专属入口待确认实际支持机制后再决定，不预设文件名。

### 4. 验证必须对应最新 HEAD

- 每次新提交后，重新读取 PR 的最新 head SHA 和该 SHA 的 CI 结果；旧提交的绿灯不能替代新 HEAD 已通过验证。
- 按改动范围运行实际可用的测试、构建和安全检查。区分“本地实际运行”“GitHub Actions 运行”“仅静态审查”。
- 未运行的测试明确标记为未运行；失败的测试先定位并修复，不删除有意义的安全检查来追求绿色。
- 代码审查、PR CI、合并后主分支 CI 和生产验收是不同证据，不可相互替代。
- 合并后检查主分支 CI 状态，以及发布工作流、部署结果和健康检查。若部署失败或线上验收未完成，明确记录阻塞并处理；PR 绿灯本身不等于生产部署成功。

### 5. 生产与高风险操作

未经用户明确授权，不进行生产部署、远程 D1 写入/迁移、生产用户数据修改或其他改变线上资源的操作。执行前应先说明目标资源、精确命令、影响范围、备份/恢复计划和验证方式，并等待明确批准。

## 最小交接记录

每次任务结束时至少记录：

- 目标与变更路径；
- 分支、PR 编号和最新 HEAD SHA；
- 开工前检查的 main SHA、相关 PR 与路径交集结果；
- 实际执行的测试及对应 SHA；
- 未验证项目、阻塞原因和下一步；
- 是否涉及生产资源（没有时明确写“未执行生产操作”）。

## 当前限制

- 路径交集检查只能发现精确文件路径冲突，不能证明不存在语义/API/运行时依赖。
- 仓库中的规则文件不能证明 GPT、DSH 或 WorkBuddy 在每一次会话中都自动加载了它；需要结合具体会话行为和实际 diff 验证。
- 本文不要求为暂时不用的第三方工具维护独立规则文件。
